# 石头剪刀布对局页交互改版需求文档

> 状态：待产品确认
> 日期：2026-08-26
> 适用版本：Gamebox Android / Godot `rps`
> 视觉原型：[rps-interaction-prototype.html](./rps-interaction-prototype.html)
> 原型提交：`f1560f1`

## 1. 文档目的

本文档定义 Gamebox 石头剪刀布双人在线对局页的完整交互改版要求，供 Godot 场景实现、状态绑定、测试和 Android 验收使用。

本文档是实现与验收的需求基线。HTML 原型用于说明布局、状态和动效方向；
当原型细节与本文档冲突时，以本文档为准。HTML 原型不是目标运行时证据，
也不代表 Godot 集成已经完成。

## 2. 背景与问题

现有对局页已经具备完整玩法、密封选择、比分、断线恢复和终局能力，但呈现存在以下问题：

1. 自己和对手的出拳状态主要依赖连续文字说明，缺少稳定、明确的空间归属。
2. 三枚可选手势虽然可点击，但选择、锁定和揭晓后的手势缩得过小，没有持续占据视觉中心。
3. 标题、赛制、比分、轮次和状态被拆成多条横向信息，纵向间距零散，屏幕利用率低。
4. 选择后的反馈只有缩放、褪色和短指示条，无法清楚区分“已点按”“提交中”“服务器已锁定”。
5. 双方揭晓只显示小型并排结果卡，缺少对局高潮和比分变化反馈。
6. 断线、终局和危险操作虽然具备功能，但需要纳入新的稳定信息层级，避免遮挡或动作竞争。

## 3. 产品目标

### 3.1 核心目标

- 让玩家无需阅读说明文字，也能一眼判断“我是否已出拳”“对手是否已出拳”“当前能否操作”。
- 让石头、剪刀、布成为页面最大、最主要的交互与视觉元素。
- 用完整的“按下 → 提交中 → 已锁定 → 同时揭晓 → 结果”动效链建立回合节奏。
- 收拢比分、轮次和状态信息，消除不必要的纵向空洞、重复文案和间距断层。
- 保持服务器权威、密封选择、断线恢复、返回、认输和自动化契约不变。

### 3.2 成功标准

改版完成后应满足：

- 在未选择、提交中、已锁定和揭晓状态下，自己与对手的区域始终可区分。
- 三枚选择热区在目标 Android 手机上均明显大于 48dp，整列可点击，无小图标式交互。
- 本地选择在服务器确认前明确显示为 pending，不提前显示为已锁定。
- 对手未揭晓前只显示等待或锁定状态，不泄露具体手势。
- 揭晓动作、回合结果和比分更新形成连续、可理解的视觉序列。
- 360×800 与 412×915 竖屏 Android 手机视口均无裁切、重叠和主操作不可见问题。

## 4. 范围与边界

### 4.1 本次范围

- Godot 石头剪刀布对局页的布局、视觉层级、手势热区和状态呈现。
- 选择、pending、锁定、揭晓、比分更新和终局的轻量动效。
- 首次加载、断线恢复、请求失败、终局、返回和认输在新布局中的呈现。
- 相关 Godot 场景测试、状态绑定测试、固定 E2E 断言和 Android UX 检查。

### 4.2 明确不在范围内

- 不修改石头剪刀布胜负规则、赛制、计分、平局处理或终局条件。
- 不修改 Go 服务端权威逻辑、协议版本、事件结构或密封选择策略。
- 不修改 Flutter 对手选择、邀请创建、赛制配置和启动流程。
- 不增加 AI、本地双人、匹配、观战、聊天、重赛、排行榜或回放。
- 不重新生成石头、剪刀、布图片；继续使用现有透明 PNG 资源。
- 不新增音效系统；音效仅作为未来可选项。
- 不把 HTML/CSS 实现或视觉截图纳入生产运行时。
- 不增加 TalkBack、屏幕阅读器、焦点顺序、大字体、WCAG 或减少动态效果验收门禁。

## 5. 游戏 UX 声明

```yaml
gameId: rps
displayName: 石头剪刀布
defaultOrientation: portrait
uxProfile: core-contract-only
inputMethods: [touch, android-back]
gameThemeRoles: []
designSystemVersion: 2.0.0
```

RPS 仅采用 Gamebox Core Contract，不选择 `Lightweight Board` 或 `Immersive` 模板。页面保留自己的上下对峙式战场，不强制套用五子棋壳层。

公共导航、状态、错误、确认和结果组件使用 Gamebox 语义令牌及共享组件；手势图片、对峙布局、比分舞台和揭晓动效属于 RPS 游戏视觉。

## 6. 设计原则

### 6.1 空间即状态

- 对手始终位于屏幕上半区，自己始终位于下半区。
- 自己的选择不得出现在对手区，对手的锁定状态不得混入自己的操作区。
- 中央区域只负责轮次、比分、回合提示和揭晓反馈，不承载常驻次要操作。

### 6.2 图片优先，文字解释

- 手势图片是主要交互元素，文字标签只负责命名和补充状态。
- 不使用带实体背景的矩形手势按钮；图片背景保持透明。
- 点击热区覆盖图片及其标签所在整列，不能只让图片像素区域可点。

### 6.3 权威状态可见

- 本地点击只进入 pending；服务器确认后才进入“已锁定”。
- pending、已锁定和失败必须有不同视觉与文案，不得只通过禁用按钮表达。
- 对手选择在双方权威揭晓前始终保密。

### 6.4 一个时刻一个主信息

- 未选择时，主信息是“选择你的手势”。
- pending 时，主信息是“正在锁定你的选择”。
- 已锁定时，主信息是“等待对手”。
- 揭晓时，主信息是回合结果。
- 断线时，主信息是恢复状态；终局时，主信息是整局结果。

## 7. 页面信息架构

页面采用四段式竖屏布局：

```text
┌──────────────────────────┐
│ 安全区 + 顶部导航         │
├──────────────────────────┤
│ 对手出拳区                │
│ 状态 + 大型未知/锁定/手势  │
├──────────────────────────┤
│ 回合舞台                  │
│ 轮次 + 比分 + 当前主信息   │
├──────────────────────────┤
│ 我的出拳区                │
│ 状态 + 三选一 / 已选手势   │
└──────────────────────────┘
```

### 7.1 比例要求

以扣除系统安全区后的可用高度为基准：

| 区域 | 建议高度 | 硬性约束 |
| --- | --- | --- |
| 顶部导航 | 9%–11% | 返回与更多操作不得进入状态栏、开孔或圆角裁切区 |
| 对手出拳区 | 29%–34% | 必须容纳大型未知、锁定或揭晓手势及状态行 |
| 回合舞台 | 17%–20% | 比分、轮次和两行以内主信息不得重叠 |
| 我的出拳区 | 剩余空间，至少 36% | 三枚选择或已选手势必须完整可见 |

布局必须由安全区和容器约束驱动，不得继续依赖只适合单一 1080×1920 画布的孤立绝对偏移。

### 7.2 间距与尺寸

- 页面水平边距使用 `spacing.page`，即 16dp。
- 同组内部使用 8dp 节奏；跨信息组使用 `spacing.section`，即 24dp。
- 顶部返回和更多操作热区至少 48×48dp。
- 三枚手势选择列等宽，列间距为 8dp。
- 每枚选择热区至少 96×128dp；在 390dp 宽参考视口上目标约为 111×142dp。
- 未揭晓的对手占位视觉宽度为屏幕宽度的 36%–44%。
- 自己锁定后的手势视觉宽度为屏幕宽度的 42%–48%。
- 选择阶段单枚手势图片视觉宽度为屏幕宽度的 23%–29%。
- 文字和主操作不得贴近底部手势导航区或被圆角屏幕裁切。

## 8. 组件要求

### 8.1 顶部导航

必须包含：

- 左侧返回按钮；可见返回与 Android 系统 Back 行为一致。
- 中间标题“石头剪刀布”。
- 标题下方显示赛制：“一局定胜负”或“三局两胜”。
- 右侧更多操作按钮，热区至少 48×48dp。

更多操作中提供“认输并结束对局”。认输不是返回行为，必须继续使用有明确后果文案的确认 Dialog。

### 8.2 玩家状态行

对手区与自己区各有一条稳定状态行，包含玩家身份和状态胶囊：

- 对手身份固定显示“对手”。
- 自己身份固定显示“你的出拳”。
- 状态胶囊可显示等待、提交中、已出拳、已揭晓、恢复中或终局。
- 每个状态胶囊只反映对应玩家的状态：一方 pending 或已锁定时只强调该方，另一方仍在等待时保持中性色；只有双方都锁定时才同时强调。
- 身份与状态的位置不得因状态文案长短左右跳动。
- 稳定连接状态不常驻显示；仅连接、恢复和失败时突出网络状态。

### 8.3 对手出拳区

根据状态只显示以下三种主视觉之一：

1. **未知**：虚线或低强调圆形占位，中间显示问号；辅助文案“对手的选择保密中”。
2. **已锁定**：使用独立锁定容器和确认符号；辅助文案“已出拳 · 等待同时揭晓”。不得显示具体手势轮廓。
3. **已揭晓**：显示对手的真实大型手势图片。

未知、锁定和真实手势不得叠加可见。

### 8.4 回合舞台

回合舞台使用稳定的 tonal surface 容器，包含：

- 轮次胶囊，例如“第 2 轮”或“最终结果”。
- 比分“你 N VS N 对手”。
- 当前主信息，最多两行：一行标题、一行辅助说明。
- 揭晓时的短暂结果横幅和冲击反馈。

比分数字必须使用等宽数字表现，更新时不推动两侧玩家标签。结果横幅只能短暂覆盖比分，动画结束后比分必须重新完整可见。

### 8.5 我的出拳区

**选择模式**：

- 按“石头、剪刀、布”顺序显示三枚等宽透明图片选择。
- 每列包含图片和中文标签。
- 整列可点击，触控区之间无死区和重叠。

**已选择模式**：

- 三选一控件退出主视觉区。
- 已选手势放大并进入稳定的“我的出拳位”。
- 旁边显示“你出了 X”和 pending、锁定或恢复文案。
- pending 与已锁定复用同一空间位置，状态变化不得造成明显跳动。

### 8.6 连接恢复横幅

- 位于顶部导航下方，覆盖或替代普通状态信息，但不得遮挡返回按钮。
- 文案为“网络波动，正在恢复对局…”及“已确认的出拳状态会保留”。
- 保留最后权威确认的界面；恢复完成前禁用新的出拳和认输提交。
- 恢复成功后安静退出，不显示普通成功 Dialog。

### 8.7 整局结果面板

- 终局结果使用底部结果面板覆盖对局现场，背景使用 scrim。
- 必须支持胜利、失败、取消和作废，不只支持胜利。
- 展示整局结果、最终比分和“返回游戏大厅”主操作。
- 面板进入前先让最后一轮揭晓动效完整播放。
- 在 360×800 视口中，主操作仍必须完整位于可见安全区内。

## 9. 状态模型与界面要求

### 9.1 核心状态矩阵

| 状态 | 对手区 | 回合舞台 | 我的区域 | 可操作性 |
| --- | --- | --- | --- | --- |
| 首次连接 | 未知占位或稳定占位 | 顶部简洁“连接中…”或“同步中…”状态 | 选择区不可用 | 禁止出拳和认输 |
| 等待选择 | 未知占位，“等待出拳” | “选择你的手势” | 三枚大型选择 | 可出拳，可打开认输确认 |
| 对手先锁定 | 锁定容器，“已出拳 · 保密” | “对手已经准备好” | 三枚大型选择 | 可出拳，可打开认输确认 |
| 本地 pending | 展示当前权威对手状态 | “正在锁定你的选择…” | 已选手势 + 进度 | 禁止重复出拳 |
| 自己已锁定 | 未知或锁定容器 | “你的选择已锁定” | 已选手势 + 已锁定 | 禁止重复出拳 |
| 双方揭晓：胜 | 对手真实手势 | 胜利横幅、原因、比分更新 | 自己真实手势 | 暂停下一轮操作直到动画结束 |
| 双方揭晓：平 | 对手真实手势 | 平局横幅、“平局不计分” | 自己真实手势 | 暂停下一轮操作直到动画结束 |
| 双方揭晓：负 | 对手真实手势 | 落败横幅、原因、比分更新 | 自己真实手势 | 暂停下一轮操作直到动画结束 |
| 断线恢复 | 保留最后权威状态 | “保留最后确认状态” | 保留 confirmed 或明确 pending | 禁止出拳和认输提交 |
| 可恢复失败 | 保留最后权威状态 | 保留回合信息 | 恢复可交互选择或 pending | 按错误类型提供重试或返回 |
| 整局终局 | 保留最后揭晓背景 | 最终比分 | 保留最后手势 | 只允许返回大厅 |

### 9.2 状态优先级

界面同时收到多个状态信号时按以下优先级呈现：

1. 认输确认 Dialog。
2. 整局终局结果。
3. 首次加载或断线恢复。
4. 回合揭晓演出。
5. 本地 pending。
6. 自己或对手锁定。
7. 等待选择。

网络横幅可以覆盖普通状态文案，但不能覆盖 Dialog、终局面板、返回按钮或最后确认状态。

### 9.3 密封选择要求

- 只有服务端权威 `rps.round.revealed` 数据可以驱动对手真实手势。
- `opponent_locked` 只能驱动锁定容器，不能推断、缓存或预加载出一个可辨认的对手手势。
- 快照同步、后台恢复和断线重连同样遵守密封规则。
- 揭晓前自动化状态标记中的 `opponent_choice_visible` 必须为 `false`。

## 10. 交互流程

### 10.1 选择与提交

1. 玩家按下任一手势，控件立即缩放反馈。
2. 松开且仍位于有效热区内时提交选择请求。
3. 请求成功写入本地 pending 后：
   - 其余两枚手势淡出并退出；
   - 已选手势移动到“我的出拳位”；
   - 文案变为“正在锁定你的选择…”；
   - 禁止第二次提交。
4. 服务端确认锁定后，pending 进度变为“已出拳”，位置保持不变。
5. 请求立即失败时，恢复三选一控件，保留刚才尝试的手势为短暂高亮，并通过 Snackbar 给出可执行的重试说明。

### 10.2 对手先出拳

1. 对手区从未知占位切换为锁定容器。
2. 状态胶囊显示“已出拳 · 保密”。
3. 中央主信息切换为“对手已经准备好 / 选择石头、剪刀或布”。
4. 自己的三枚选择保持可用，不进行倒计时，不泄露对手选择。

### 10.3 同时揭晓

1. 收到权威揭晓事件后，冻结新的选择输入。
2. 对手手势从上方向中央进入；自己手势从下方向中央进入。
3. 两个手势在中央形成一次冲击反馈。
4. 显示“本轮获胜”“本轮平局”或“本轮落败”横幅。
5. 显示胜负原因，例如“布包住石头”，并更新比分。
6. 非终局在演出结束后进入下一轮选择状态；终局进入整局结果面板。

### 10.4 下一轮

- 揭晓演出总时长结束前，不允许下一轮提交，即使服务端状态已经允许。
- 演出结束后，双方手势退出，选择区重新进入。
- 上一轮结果不保留为占据大块空间的常驻卡片；比分和当前轮次已经承担历史反馈。
- 平局不增加比分，主信息明确提示“平局不计分，再来一轮”。

### 10.5 返回与认输

- 可见返回和 Android 系统 Back 都返回游戏大厅，不发送认输请求。
- 活跃对局返回大厅后仍可恢复。
- 若认输确认 Dialog 已打开，Back 只关闭 Dialog。
- “认输并结束对局”必须先打开确认 Dialog。
- Dialog 标题：“认输并结束本局？”
- Dialog 说明：“确认后对手立即获胜，本局无法继续。”
- 取消操作：“继续对局”。
- 危险操作：“认输并结束”。
- 只有点击危险操作后才可发送一次认输请求；提交期间禁止重复操作。

## 11. 动效需求

动效必须轻量、可由 Godot 稳定复现，并优先使用 `GameboxTokens.MOTION`。动效不得改变权威状态，只负责呈现已经发生的状态转换。

### 11.1 动效时序

| 动作 | 时长 | 要求 |
| --- | --- | --- |
| 手势按下 | `fast`，100ms | 以控件中心缩放至约 0.92，松开恢复或进入选择动画 |
| 其余选择退出 | `standard`，200ms | 降低透明度并向下轻移，不突然消失 |
| 已选手势入位 | `slow`，300ms | 从选择列移动到稳定的“我的出拳位” |
| 锁定状态进入 | `slow`，300ms | 锁定容器缩放或淡入一次，结束后保持静态 |
| 双方手势进入 | 300ms | 上下相向进入，带轻微 overshoot |
| 冲击反馈 | 200ms | 中央扩散环或闪光，不遮挡手势内容 |
| 结果横幅 | 约 1200ms | 弹入、短暂停留、淡出；淡出后比分完整可见 |
| 比分跳动 | 300ms | 仅变化的一侧数字轻微放大后恢复 |
| 结果面板进入 | `pageEnter`，400ms | 最后一轮演出完成后从底部进入 |

### 11.2 动效约束

- 揭晓演出从手势进入到下一轮解锁总时长建议为 1400–1800ms。
- 不能使用无限循环的大幅呼吸、旋转或闪烁。
- 锁定后可以有一次短脉冲，但结束后必须稳定，避免制造仍在处理的错觉。
- pending 进度可以循环，但必须和已锁定状态在图形及文案上明显不同。
- 离开页面、进入后台、断线或终局时必须停止无意义的进行中动画。
- 音效和触觉反馈为 MAY；若加入，不能成为理解状态的唯一方式。

## 12. 视觉与令牌要求

### 12.1 MUST

- 公共颜色、文字、间距、圆角、状态和动效必须使用生成的 Gamebox 语义令牌。
- 明暗模式必须使用 Gamebox Teal `#006B60` 生成的现有 light/dark scheme。
- 容器与文字必须使用匹配的 container / on-container 角色。
- `error` 只用于失败和危险，不用于普通落败结果装饰。
- 三张透明手势图片在明暗模式下均保持可辨认，不增加不透明矩形按钮底。
- 保留 `RockButton`、`ScissorsButton`、`PaperButton`、`BackButton`、
  `RevealPanel`、`ResignDialog`、`LoadingOverlay` 和 `ResultPanel` 等现有
  自动化节点契约，允许在其内部增加布局子节点。

### 12.2 SHOULD

- 页面主要依靠 tonal surface 层级，不使用大面积阴影切割区域。
- 手势图片只使用轻量投影以从背景中分离。
- 回合舞台使用稳定容器，状态切换时不改变整体高度。
- 状态胶囊使用图形、颜色和文字的组合，不只依赖颜色。
- 长度正常的中文文案保持一至两行，不推动主操作离开安全区。

### 12.3 MAY

- 揭晓冲击可使用一次扩散环、微弱背景光晕或粒子。
- 本轮获胜可使用轻量成功色强调；落败保持克制，不使用错误 Dialog。
- 可加入一次轻触觉反馈或短促游戏音效，但不在本次必要交付范围内。

## 13. 文案基线

| 场景 | 主文案 | 辅助文案 |
| --- | --- | --- |
| 等待选择 | 选择你的手势 | 手势会在双方锁定后同时揭晓 |
| 对手先锁定 | 对手已经准备好 | 选择石头、剪刀或布 |
| 本地 pending | 正在锁定你的选择… | 服务器确认前不会视为最终出拳 |
| 自己已锁定 | 你的选择已锁定 | 等待对手后同时揭晓 |
| 对手未知 | 等待出拳 | 对手的选择保密中 |
| 对手已锁定 | 已出拳 · 保密 | 等待同时揭晓 |
| 本轮胜利 | 本轮获胜 | 显示具体克制关系，比分已更新 |
| 本轮平局 | 本轮平局 | 平局不计分，再来一轮 |
| 本轮落败 | 本轮落败 | 显示具体克制关系，比分已更新 |
| 断线恢复 | 保留最后确认状态 | 恢复完成前暂停新的操作 |
| 整局胜利 | 你赢得了对局 | 显示最终比分和赛制 |
| 整局失败 | 对手赢得了对局 | 显示最终比分和赛制 |
| 取消 | 对局已取消 | 返回游戏大厅 |
| 作废 | 对局已作废 | 返回游戏大厅 |

具体克制关系使用：

- 石头砸碎剪刀。
- 剪刀剪开布。
- 布包住石头。
- 双方相同时使用“都是石头”“都是剪刀”或“都是布”。

不得显示协议类型、内部错误码、revision、URL、token、match ID 或对手未揭晓的选择。

## 14. 加载、失败与恢复

### 14.1 首次连接

- 使用共享 `ConnectionBanner` 在顶部显示简洁的“连接中…”或“同步中…”状态，不使用全屏 `LoadingOverlay`。
- 保留稳定的对局页面和占位内容，不用连接状态覆盖主视觉区域。
- 未收到有效权威快照前，不显示可操作的选择状态。
- 赛制、比分和轮次没有数据时显示稳定占位，不显示虚构结果。

### 14.2 出拳失败

- 立即请求失败：恢复选择模式，保留刚才尝试的手势为短暂视觉提示，Snackbar 显示“出拳失败，请重试”。
- 权威拒绝或冲突：以服务端安全错误映射为准，重新同步或恢复可操作状态。
- 已锁定后收到重复请求错误：维持已锁定权威状态，不退回选择模式。

### 14.3 断线与后台恢复

- 保留最后权威确认的比分、轮次、手势锁定和揭晓状态。
- 若本地选择尚未确认，显示“提交结果待确认”，不得标为已锁定。
- 恢复期间禁止出拳和认输请求。
- 收到新快照后以快照重建页面；不能继续播放与快照不一致的旧揭晓动画。
- 恢复失败时提供“重试”或“返回游戏大厅”，不使用无操作出口的阻塞页面。

## 15. 实现边界

### 15.1 预计修改文件

- `game_runtime/games/rps/rps_scene.tscn`：安全区、容器布局、双方出拳区、回合舞台和终局布局。
- `game_runtime/games/rps/rps_controller.gd`：状态到新组件的绑定、Tween 时序和动画锁。
- `game_runtime/test/test_rps_state.gd`：场景契约、状态呈现和触控布局测试。

按实际测试结构可以增加 RPS 专用场景测试文件，但不应把 RPS 手势组件提升为跨游戏公共组件，除非出现第二个真实消费者。

### 15.2 必须保留

- `rps_state.gd` 的服务器权威 reducer 语义。
- 三个选择按钮的节点名称、顺序和请求值：`rock`、`scissors`、`paper`。
- pending、锁定、揭晓和终局的现有协议绑定。
- `GAMEBOX_GODOT_READY`、`GAMEBOX_RPS_STATE`、
  `GAMEBOX_RPS_PRESENTATION` 和 `GAMEBOX_MATCH_RESULT` 等自动化日志契约。
- 可见返回、Android Back、认输确认和返回大厅回调。
- 现有透明图片资源：
  - `game_runtime/games/rps/assets/rock.png`
  - `game_runtime/games/rps/assets/scissors.png`
  - `game_runtime/games/rps/assets/paper.png`

### 15.3 禁止事项

- 客户端自行计算并提前呈现胜负、比分或终局。
- 为了动画延迟服务端事件应用、丢弃事件或篡改 reducer 状态。
- 在揭晓前把对手图片纹理设置成真实选择后仅靠透明度隐藏。
- 用 HTML 截图、静态 mock、golden 或 headless 场景替代 Android 真机/模拟器 UX 检查。
- 把截图采集、裁切、SSIM 或像素比较加入固定确定性 E2E。

## 16. 测试需求

### 16.1 Godot 场景与状态测试

必须覆盖：

- 竖屏场景、节点契约和手势按钮顺序不变。
- 360×800 与 412×915 逻辑视口下安全区、无重叠和无溢出。
- 三枚手势热区等宽；每枚宽度至少 96dp、高度至少 128dp，且整列可点击。
- 默认、pressed、pending、已锁定、disabled、揭晓和终局视觉状态。
- 对手锁定前后均不泄露具体选择。
- pending 请求成功、权威接受、权威拒绝和恢复选择。
- 胜、平、负三种揭晓，比分只使用权威数据。
- 非终局演出结束后进入下一轮；终局演出后进入结果面板。
- 首次加载、断线恢复、恢复失败和后台同步。
- 可见返回与系统 Back 不发送认输。
- 认输取消不发送请求，确认只发送一次。
- light/dark、普通字号中文文案和安全区布局。

### 16.2 固定两设备 E2E

固定 E2E 必须继续验证：

- 邀请、启动和赛制显示。
- 自己 pending 与权威锁定。
- 对手选择在揭晓前不可见。
- 双方锁定后的权威揭晓和比分更新。
- 平局续轮与三局两胜终局。
- 断线、强停、重连和权威快照恢复。
- 返回大厅后对局可恢复。
- 认输确认前不发送请求。

固定 E2E 只记录状态标记、生命周期、协议和权威断言，不采集截图。

### 16.3 仓库门禁

实现完成后运行：

- RPS 聚焦 Godot 测试。
- 全部 Godot 测试。
- 设计令牌/schema/生成映射检查；若令牌未修改，也必须确认无漂移。
- 仓库现有快速与完整验证门禁。
- Android 构建与两设备 E2E。

若修改任何仓库自有测试或验收 runner，其成功默认输出必须保持紧凑；失败时输出失败阶段及相关 stdout/stderr，并保留原始非零退出码。

## 17. Android 目标运行时 UX 验收

### 17.1 目标设备

- Android 手机，固定 portrait。
- 窄屏参考：360×800 逻辑视口。
- 大屏参考：412×915 逻辑视口。
- 使用实际构建的 Flutter 宿主与打包 Godot 游戏，不使用 HTML 原型替代。

### 17.2 必查状态

实现者必须在 light/dark 适用状态下捕获并亲自检查：

1. 首次同步。
2. 双方均未出拳。
3. 对手先锁定。
4. 本地 pending。
5. 自己已锁定等待对手。
6. 本轮获胜揭晓。
7. 本轮平局揭晓。
8. 本轮落败揭晓。
9. 断线恢复并保留已确认状态。
10. 可恢复错误与重试。
11. 认输确认 Dialog。
12. 整局胜利与整局失败结果面板。
13. Android 系统 Back 与可见返回。
14. 后台恢复后重新同步。

### 17.3 每个状态的检查项

- 自己与对手空间归属是否明确。
- 主手势是否足够大且无裁切。
- 状态胶囊、主文案和比分是否互不竞争。
- 选择热区是否连续、易点且无误触。
- pending、锁定、揭晓是否能在不读辅助文案时区分。
- 状态变化是否无明显跳版、残影或动画冲突。
- 结果面板主操作是否完整位于安全区。
- 无邀请凭据、token、内部地址、revision 或个人隐私进入画面。

截图是临时检查输入，不要求提交、保留、上传或附在 PR 中。未亲自检查这些目标运行时状态时，UI 改版不能判定为完成。

## 18. MUST、SHOULD 与 MAY 汇总

### 18.1 MUST

- 上下对峙式区域与中央回合舞台。
- 大型透明手势热区和已选手势放大展示。
- pressed、pending、locked、reveal、failure 明确区分。
- 服务端权威、密封选择和比分/终局数据不变。
- 安全区、48dp 公共控件、返回与认输确认语义。
- 首次加载、断线恢复、错误和终局完整覆盖。
- Gamebox 语义令牌、light/dark 和节点/自动化契约。
- Godot、仓库门禁、两设备逻辑 E2E 与 Android UX 检查。

### 18.2 SHOULD

- 使用文档给出的区域比例、手势尺寸和文案基线。
- 回合舞台高度稳定，状态切换不推动页面结构。
- 揭晓总时长保持 1400–1800ms，节奏清晰但不过长。
- 结果横幅自动退出，比分在演出后完整可见。
- 只在连接异常时突出网络状态。

任何 SHOULD 偏离必须在实现评审中记录原因和替代措施。

### 18.3 MAY

- 一次轻量触觉反馈。
- 一次冲击粒子或背景光晕。
- 未来加入短音效。

MAY 项不得扩大为本次交付阻塞项。

## 19. 完成定义

只有同时满足以下条件，改版才可判定为 `complete`：

- [ ] 新布局和所有核心状态已集成到实际 Godot 场景。
- [ ] 服务器权威和揭晓前保密断言通过。
- [ ] 选择、pending、锁定、揭晓和终局动效按要求工作。
- [ ] 返回、Android Back、认输确认和恢复行为通过。
- [ ] 聚焦测试、全部 Godot 测试、仓库完整门禁和 Android 构建通过。
- [ ] 固定两设备 E2E 通过，且未加入截图断言。
- [ ] 在窄屏与大屏 Android 竖屏视口检查受影响状态。
- [ ] 实现者已亲自检查目标运行时截图并报告 UX 结论。

- [ ] 完成审计按“Scope / MUST / SHOULD / MAY / Tests / UX inspection / Verdict”顺序给出。
