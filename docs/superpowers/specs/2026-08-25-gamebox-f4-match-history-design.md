# Gamebox F4 个人战绩与统计设计

- 日期：2026-08-25
- 状态：对话设计已确认，等待书面规格审核
- 适用范围：Gamebox Flutter App、Go 服务端与 SQLite 迁移
- UX 基线：[`gamebox-material-3-ux`](../../../.agents/skills/gamebox-material-3-ux/SKILL.md) 的 Flutter App 与 Core Contract 规范

## 1. 背景与目标

Gamebox 已保存五子棋对局、参与者和权威事件，但用户目前无法在 App 中查看已结束的个人对局或自己的胜负统计。F4 首版提供一个简单、只读、服务端权威的“我的战绩”页面。

本期目标：

1. 用户可从首页明确进入自己的战绩页。
2. 页面展示有效对局、胜、负、和与胜率。
3. 页面按结束时间倒序展示已结束和已作废的个人对局。
4. 数据复用现有权威对局与事件，不新建第二套战绩真相源。
5. 通过自动化测试和真实 Android 运行时截图完成验收。

## 2. 已确认范围

### 2.1 包含

- 只查看当前登录用户的五子棋战绩。
- 统计有效对局数、胜、负、和与胜率。
- 记录胜、负、和、认输导致的正常胜负，以及双方持续离线导致的作废。
- 单条记录展示结果、对手昵称、执黑/执白、结束时间与总手数。
- 时间倒序、基于游标的自动分页。
- 加载、空、错误、有数据和加载更多失败状态。

### 2.2 明确不做

- 不提供棋局回放、自动播放、详情页或记录点击行为。
- 不提供结果、日期、对手或游戏筛选。
- 不提供排行榜、公开战绩、分享或其他用户的记录。
- 不展示活跃对局；活跃对局继续由首页承载。
- 不展示零手取消的对局，也不将它纳入统计。
- 不修改 Godot、WebSocket 实时协议或五子棋规则。
- 不新增 Navigation Bar，不修改设计令牌体系。

## 3. 产品语义

### 3.1 对局结果

服务端从当前用户视角返回以下四种展示结果，Flutter 不根据底层字段再次推断：

| `outcome` | 语义 | 是否纳入有效对局与胜率 |
| --- | --- | --- |
| `win` | `winner_user_id` 是当前用户；包含五子连线或对手认输 | 是 |
| `loss` | `winner_user_id` 是对手；包含五子连线或当前用户认输 | 是 |
| `draw` | 对局正常和棋 | 是 |
| `abandoned` | 双方持续离线超时作废 | 否 |

认输只影响底层结束原因，首版列表仍以普通“胜”或“负”展示。

### 3.2 统计

- `validMatches = wins + losses + draws`
- `winRate = wins / validMatches`
- `validMatches` 为 0 时，`winRate` 返回 `0`。
- `winRate` 是 `0` 到 `1` 的有限数值；Flutter 只负责按百分比格式化展示。
- `abandoned` 与 `cancelled` 均不进入有效对局和胜率计算。

### 3.3 总手数

总手数是该对局中 `gomoku.move.accepted` 事件的数量。不得直接使用 `matches.revision`，因为认输、取消和作废等终局事件也会增加 revision。

## 4. 总体架构与数据流

F4 只增加一条读链路：

```text
HomePage
   └── 我的战绩 ──> MatchHistoryPage
                          │
                          └── MatchHistoryController
                                  │
                                  └── MatchHistoryApi
                                          │
                                          └── GET /v1/games/gomoku/history
                                                  │
                                                  └── matches + match_players
                                                       + users + match_events
```

- Go 服务端负责身份边界、结果归类、统计、手数和分页。
- Flutter 使用独立 API、模型、controller 和 page，不把战绩加载状态塞入现有 `HomeController`。
- 页面使用普通 Flutter `Navigator` 二级路由；可见返回按钮与 Android 系统返回都执行同一导航结果。
- 不引入战绩汇总表、物化视图或客户端缓存数据库。

## 5. HTTP API 契约

### 5.1 请求

```http
GET /v1/games/gomoku/history?cursor=<opaque>&limit=20
Authorization: Bearer <access-token>
```

- `cursor` 可选；缺省时从最新记录开始。
- `limit` 可选，默认 20，范围 1–50。
- 接口只使用通过鉴权中间件得到的当前用户 ID，不接受用户 ID 查询参数。
- 使用与现有 HTTP API 一致的 JSON 响应和错误外壳。

### 5.2 成功响应

```json
{
  "statistics": {
    "validMatches": 8,
    "wins": 5,
    "losses": 2,
    "draws": 1,
    "winRate": 0.625
  },
  "matches": [
    {
      "id": "11111111-1111-4111-8111-111111111111",
      "outcome": "win",
      "opponentNickname": "棋手乙",
      "color": "black",
      "finishedAt": 1787623200000,
      "moveCount": 57
    }
  ],
  "nextCursor": "eyJ2IjoxLCJmaW5pc2hlZEF0IjoxNzg3NjIzMjAwMDAwLCJtYXRjaElkIjoiLi4uIn0"
}
```

- `finishedAt` 延续现有 API 的 UTC Unix 毫秒契约；Flutter 按设备本地时区显示。
- `color` 只能是 `black` 或 `white`。
- `moveCount` 是非负整数。
- 没有更多记录时 `nextCursor` 为 `null`。
- 每一页都返回请求时的最新统计；Flutter 在加载更多成功后使用该值更新顶部统计。

### 5.3 排序与游标

- 排序固定为 `finished_at DESC, match_id DESC`。
- 翻页使用严格的 keyset 条件：`finished_at < cursor.finishedAt OR (finished_at = cursor.finishedAt AND match_id < cursor.matchId)`。
- 游标是无 padding 的 base64url 编码 JSON，包含版本、`finishedAt` 和 `matchId`；它对客户端是 opaque 值。
- 服务端严格校验 base64url、JSON 字段集合、版本、数值范围和规范 match UUID。
- 未来新对局在分页期间结束时，keyset 保证旧游标继续向更旧方向查询，不因偏移量变化导致重复。

### 5.4 错误

| 场景 | HTTP 状态 | 行为 |
| --- | --- | --- |
| 缺少、无效或过期 access token | `401` | 进入现有会话恢复/登出流程 |
| `limit` 越界、重复参数、未知参数或游标非法 | `400` | 返回明确的无效请求错误 |
| 数据库、不可能的对局组合或数据损坏 | `500` | 整个请求失败，不跳过坏记录、不返回半页数据 |

服务端记录可定位的阶段和错误分类，但不记录 access token、完整游标或其他敏感值。

## 6. 服务端数据设计

### 6.1 真相源

查询复用：

- `matches`：状态、结束原因、获胜用户和结束时间。
- `match_players`：当前用户与对手成员关系、黑白方。
- `users`：对手当前昵称。
- `match_events`：`gomoku.move.accepted` 手数。

不重放整盘棋来判定胜负；胜负使用已由现有权威对局服务落库的 `status`、`result` 和 `winner_user_id`。

### 6.2 可见记录

列表只包含：

- `game_id = 'gomoku'`
- `status = 'finished'` 且结果可验证为胜、负或和
- `status = 'abandoned'`
- `finished_at IS NOT NULL`
- `match_players` 中存在且仅存在当前用户对应成员，并能解析唯一对手

`active` 和 `cancelled` 无条件排除。遇到终局状态、结果、获胜者、成员或颜色不一致时，查询返回内部错误，不猜测或隐藏损坏数据。

### 6.3 一致性与索引

- 单次请求在同一 SQLite 只读事务中读取统计和列表页，保证两者针对同一快照。
- 新增迁移只添加战绩查询必需的索引，预计至少覆盖 `match_players(user_id, match_id)`。
- 是否增加额外 `matches` 复合索引，由实施时的 `EXPLAIN QUERY PLAN` 证据决定；不为未经证实的查询添加冗余索引。
- 迁移必须使用现有顺序、幂等和 schema 验证机制。

## 7. Flutter 页面与交互

### 7.1 导航与首页入口

- 在首页用户信息区域增加带文字的“我的战绩”入口。
- 入口使用 `OutlinedButton` 级别，不与游戏卡中唯一的主操作争夺强调。
- 为入口提供稳定语义标识 `open-match-history`。
- 战绩是从当前唯一一级目的地进入的二级页，不增加 Navigation Bar。

### 7.2 页面结构

- 使用小型 Material 3 Top App Bar，标题为“我的战绩”。
- 显示可见返回按钮，并与 Android 系统返回导航到同一首页实例。
- 主体复用 `GameboxPageBody` 与现有页面边距、宽度约束和安全区行为。
- 顶部统计卡展示胜率、有效对局、胜、负和和。
- 统计卡下方是“最近对局”标题和单列只读记录。
- 记录行不可点击，不使用暗示可导航的箭头、ink response 或按钮语义。

### 7.3 视觉语义

- 所有颜色、字体、间距、形状和动效只使用现有 Material 3 语义令牌或公共组件。
- “胜”使用主色容器；“负”使用中性容器；“和”使用第三色容器；“作废”使用中性弱化样式。
- `error` 仅表示真实错误或危险，不用于普通败局。
- 结果不仅依靠颜色；必须同时显示“胜”、“负”、“和”或“作废”文字。
- 普通文字在窄屏、大字号和明暗主题下不得裁切。
- 所有交互目标至少 48×48dp。

### 7.4 页面状态

| 状态 | 显示与行为 |
| --- | --- |
| 首次加载 | 在稳定页面区域显示明确加载态，不因内容替换产生明显跳动 |
| 空 | 页内显示“还没有已结束的对局”，不显示无意义的加载更多控件 |
| 首次加载失败 | 使用页内 `GameboxAsyncPanel` 表达错误并提供重试，不用 Snackbar 承载主要错误 |
| 有数据 | 显示统计卡与已加载的记录，滚动到底部自动请求下一页 |
| 加载更多 | 保留已有数据，列表底部显示内联进度 |
| 加载更多失败 | 保留已有数据，列表底部显示错误和重试；不清空页面 |
| 无更多数据 | 停止触发翻页，不添加额外弹窗或提示 |

首版不增加下拉刷新。重新进入页面即获取最新数据。

## 8. 状态管理

`MatchHistoryController` 保持一个可区分的页面状态：

- 初始加载是独立状态。
- 成功状态同时保有统计、去重后的记录、`nextCursor`、是否正在加载更多以及可恢复的加载更多错误。
- 加载更多期间忽略重复触发，防止同一游标并发请求。
- 追加记录以 match ID 去重，同时保留服务端顺序。
- controller 或 page 销毁后，迟到请求不得再通知 UI。
- `401` 交给现有认证恢复边界处理；普通页面错误不擅自清除会话。

## 9. 安全、隐私与可访问性

- 所有战绩请求必须鉴权，并且只以 token 对应用户为查询主体。
- 服务端测试必须证明用户 A 无法通过查询参数、游标或其他输入读取用户 B 的记录。
- 返回对手昵称是现有已登录对手发现模型内容；首版不额外返回对手 ID、在线状态或其他资料。
- 页面使用稳定 `Key` 和 `Semantics` 标识首页入口、返回按钮、加载区、错误重试、统计卡和记录行。
- 记录的语义文本必须包含结果、对手、棋子颜色、结束时间和总手数，不把信息只拆成无上下文的数字。
- 截图、日志和测试产物不得包含 token、邀请码或真实用户敏感数据。

## 10. 测试与验收

### 10.1 Go 服务端

- 服务层测试：无记录、胜、负、和、双方离线作废、五子连线与认输的结果映射。
- 统计测试：认输计入普通胜负，作废和取消不进入有效对局，零有效对局的胜率为 0。
- 手数测试：只计数 `gomoku.move.accepted`，认输或作废 revision 不被误算成落子。
- 分页测试：同时间截使用 match ID 稳定排序，跨页不重复、不漏掉已存在的更旧记录，无下一页时游标为 `null`。
- 校验测试：无效 limit、未知/重复查询参数、非法 base64url、额外 JSON 字段、非法版本、溢出时间和非规范 UUID。
- HTTP 测试：身份隔离、`401`/`400`/`500` 映射、成功 JSON 契约和 method fallback。
- 数据完整性测试：成员、颜色、获胜者或终局字段损坏时整个请求失败。
- 迁移测试：干净库和旧库均可迁移，索引列顺序与 schema 校验通过。

### 10.2 Flutter

- API 解析测试：完整响应、空列表、可选游标、所有枚举值与非法数据。
- controller 测试：首次成功/失败/重试、加载更多、并发抑制、追加去重、加载更多失败保留内容与销毁后迟到完成。
- Widget 测试：首页入口、加载、空、错误、重试、统计、四种结果、不可点击记录、底部加载/错误和明暗主题。
- 导航测试：可见返回按钮和模拟 Android 系统返回都返回首页，且不创建新首页状态。
- 布局测试：目标手机宽度、大文字缩放与长昵称不出现 overflow 或文本裁切。

### 10.3 端到端与视觉证据

- 固定 E2E 通过稳定语义标识验证首页入口、进入战绩页、统计与列表内容、可见返回和 Android 系统返回。
- 固定 E2E 不保留截图，不把截图编码到 fixture 或日志。
- 实施完成后运行仓库完整验证门禁。
- 另外构建并运行真实 Android App，截取不含敏感信息的首页入口和有数据战绩页。
- 真实运行时视觉验收至少覆盖亮色、暗色、窄屏手机与返回行为；当一张截图不足以证明这些状态时使用多张。
- HTML 预览、Widget 测试、fixture 和静态渲染都不替代真实 Android 运行时截图。

## 11. 交付顺序

1. 新增失败的 Go 服务层与 HTTP 契约测试。
2. 实现只读查询、严格游标、路由和必要索引。
3. 新增失败的 Flutter API、controller 和 Widget 测试。
4. 实现 Flutter 数据层、战绩页和首页入口。
5. 补充固定 E2E 的战绩流程，不在 E2E 中保留截图。
6. 运行完整验证，并在真实 Android 运行时完成视觉验收。

实施必须遵循测试驱动：先看到新测试因缺失行为而失败，再写最小实现使其通过。

## 12. 完成标准

F4 首版只有在以下条件全部满足后才算完成：

- 已登录用户能从首页进入且只查看自己的五子棋战绩。
- 统计与列表对胜、负、和、认输、作废和取消的语义符合本设计。
- 列表字段、倒序排序、手数和游标分页正确且稳定。
- 页面没有回放、筛选、详情、排行榜或其他未批准范围。
- 加载、空、错误、有数据和加载更多失败都有可操作的稳定状态。
- 可见返回与 Android 系统返回一致，不破坏首页或活跃对局状态。
- Go、Flutter、迁移、契约与固定 E2E 测试全部通过。
- 仓库完整验证门禁通过。
- 已附上真实 Android 应用截图，证明首页入口、战绩页、亮/暗主题和目标手机布局。

## 13. 后续但不在本期

棋局回放、筛选、详情页、公开战绩、排行榜与分享均需要新的产品设计和审批，不因现有 `match_events` 可用而自动进入 F4 首版。
