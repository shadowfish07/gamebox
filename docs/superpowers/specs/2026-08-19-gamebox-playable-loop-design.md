# Gamebox 首个可玩闭环设计

- 日期：2026-08-19
- 状态：对话设计已确认，等待书面规格审核
- 本期目标：在两台 Android 模拟器上完成从邀请码注册到一局联网五子棋结束及断线恢复的闭环

## 1. 背景与目标

Gamebox 是一个必须登录才能使用的 Android 游戏集。Flutter 承载账号、用户资料和游戏大厅，Godot 承载独立游戏，Go 服务端维护联网对局的权威状态。首个游戏为五子棋。

本期优先验证最重要的技术和产品链路：

1. Flutter 与 Godot 可以稳定打包进同一个 Android App。
2. 两个用户可以使用一次性邀请码注册并自动登录。
3. 空闲用户可以选择另一位空闲用户并立即创建五子棋对局。
4. Godot 客户端通过 WebSocket 接收服务端权威状态并完成一局游戏。
5. App 退出、客户端断线和服务端重启不会丢失已确认的棋步。
6. 两台 Android 模拟器能够通过本机 Go 服务完成真实端到端验收。

## 2. 本期范围

### 2.1 身份与用户

- App 未登录时不能进入游戏大厅或游戏。
- 管理脚本可以一次生成 N 个一次性邀请码。
- 用户首次注册输入邀请码和昵称。
- 邀请码只允许成功消费一次；创建用户和消费邀请码必须在同一个数据库事务中完成。
- 昵称全局唯一，忽略大小写和首尾空格，长度为 2–16 个字符。
- 注册成功后签发短期 access token 和长期 refresh token，App 后续自动登录。
- 本期不提供密码、游客模式或设备迁移入口。

### 2.2 游戏大厅与对手选择

- 首页以游戏目录展示五子棋，并为未来游戏保留通用 `gameId`。
- 每个用户同一时间最多参与一场五子棋对局。
- 用户有活跃五子棋对局时，首页只提供继续该对局的入口，不能发起新对局。
- 用户空闲时可以进入对手选择页面。
- 对手列表包含除自己外的已启用用户。
- 正在参与五子棋的用户显示为“游戏中”且不可选择。
- 离线但空闲的用户仍可被选择。
- 选择对手后直接创建对局，不需要对方接受。
- 尚未产生任何落子的对局可以由任一方无损取消；取消不计胜负。
- 双方同时或并发发起对局时，服务端保证一个用户只会被一个成功事务占用。失败方刷新状态并看到明确提示。

### 2.3 五子棋规则

- 棋盘为 15×15。
- 服务端随机分配黑白方，黑方先行。
- 横、竖或斜线连续 5 颗或以上同色棋子即获胜。
- 不使用三三、四四或长连禁手。
- 棋盘下满且没有获胜方时判和棋。
- 产生首步后允许认输；认输时对方获胜。
- 客户端可以做本地合法性提示，但只有服务端可以接受动作、改变轮次或宣告结果。

### 2.4 断线与结束

- WebSocket 心跳超时 45 秒后，玩家被视为离线。
- 只有双方都离线时才写入 `both_offline_since` 并开始计算作废时间。
- 任一方重新连接后立即清除双方离线时间。
- 双方持续离线满 24 小时后，对局进入 `abandoned` 状态，不计任何一方胜负。
- 返回 Flutter 大厅、App 进入后台或 Godot Activity 退出都不等于认输。
- 服务端重启后从 SQLite 恢复活跃对局和棋步；重启后没有活动连接的对局按离线状态继续处理。

### 2.5 本期运行与验收环境

- 客户端只实现 Android。
- 验收使用两台 Android 模拟器连接宿主机上的 Go 服务。
- 服务地址通过构建或运行配置注入，模拟器本地开发默认使用宿主机可访问地址。
- 本期不要求 Cloudflare Tunnel、公网真机或开机自启。

## 4. 总体架构

### 4.1 仓库边界

```text
gamebox/
├── app/                    # Flutter 游戏大厅和 Android 宿主
├── game_runtime/           # Godot 游戏运行时
│   ├── core/               # 游戏注册、连接和通用生命周期
│   └── games/gomoku/       # 五子棋场景与表现
├── server/                 # Go 服务端和管理 CLI
├── protocol/               # 版本化协议定义与示例
├── tool/                   # 构建、测试和双模拟器 E2E
└── docs/                   # 规格与实施计划
```

### 4.2 Android App

Flutter 是 App 的入口和平台壳，负责：

- 注册、自动登录和昵称；
- 游戏目录、首页状态和对手选择；
- 创建或继续对局；
- 通过通用 `GameLauncher` 启动游戏。

Android 实现通过 Kotlin 桥接启动全屏 `GodotActivity`。桥接层只传递 `gameId`、启动票据和必要的非敏感配置，不包含业务规则。首版锁定竖屏，并保证一个进程内最多运行一个 Godot Engine 实例。

Godot 负责：

- 根据 `gameId` 从 `GameRegistry` 加载对应 `PackedScene`；
- 棋盘、输入、动画和对局内 UI；
- WebSocket 连接、事件顺序、快照应用和自动重连；
- 把玩家意图提交给服务端，并只应用服务端确认的权威事件。

### 4.3 Go 服务端

Go 服务端为单进程、单二进制，HTTP API 与 WebSocket 共用同一服务。内部划分为：

- `auth`：邀请码、access token、refresh token；
- `users`：昵称、用户状态和对手列表；
- `games`：游戏目录与规则注册；
- `matches`：游戏槽位、对局生命周期、连接和重连；
- `games/gomoku`：玩家数、单局限制、棋盘、轮次和胜负；
- `store`：SQLite 事务与迁移；
- `cmd/gameboxctl`：生成和管理邀请码。

### 4.4 多游戏扩展边界

首版只实现五子棋，不提前构建通用游戏 DSL。后续扩展依赖三个窄接口：

1. Flutter 的 `GameCatalog` 和 `GameLauncher.launch(gameId, launchTicket)`。
2. Godot 的 `GameRegistry`，把 `gameId` 映射到独立游戏场景。
3. Go 的规则注册表，把 `gameId` 映射到独立的规则引擎和状态快照逻辑。

身份、连接、心跳、事件顺序、对局和事件持久化属于平台共享能力。玩家数量、并发限制、动作合法性、胜负条件和游戏表现属于每个游戏模块。一个用户只能参加一场的限制只属于五子棋，不会成为所有游戏的全局限制。

## 5. 协议与数据流

### 5.1 协议外壳

控制消息采用版本化 JSON。公共外壳为：

```json
{
  "protocolVersion": 1,
  "gameId": "gomoku",
  "matchId": "match_123",
  "revision": 16,
  "type": "gomoku.move.accepted",
  "actionId": "optional-client-action-id",
  "payload": {}
}
```

`payload` 由具体游戏解释。客户端动作携带唯一 `actionId` 和 `expectedRevision`，服务端据此去重并拒绝基于旧状态的动作。

### 5.2 注册

1. `gameboxctl` 生成高熵邀请码，只显示一次明文，数据库只保存摘要。
2. Flutter 提交邀请码和规范化昵称。
3. 服务端在同一事务中验证邀请码、检查昵称、创建用户并消费邀请码。
4. 成功后返回 access token 和 refresh token。
5. refresh token 仅存于 Android 安全存储；服务端保存可撤销摘要。

### 5.3 创建对局

1. Flutter 获取当前五子棋状态和对手列表。
2. 用户选择一位空闲对手。
3. 服务端在一个事务中锁定并再次验证双方状态。
4. 服务端随机分配黑白，创建 `active` 对局，并为双方写入唯一游戏槽位。
5. 任一步骤失败都回滚，不产生半局或单边占用。
6. Flutter 请求一次性 launch ticket 并启动 Godot。

### 5.4 启动票据和恢复令牌

- Flutter 使用登录态请求一次性 launch ticket；票据只绑定一个用户、一场对局和一个游戏，60 秒后过期。
- Godot 建立 WebSocket 时消费 launch ticket。
- 连接成功后服务端返回仅限本局的 resume token。
- resume token 使用滑动 30 分钟失效窗口，只能恢复同一用户的同一对局连接，并在对局终止时立即失效。
- 长时间离线导致 resume token 失效时，Godot 返回 Flutter；Flutter 使用登录态获取新的 launch ticket 后重新进入。

### 5.5 一次落子

1. Godot 提交坐标、`actionId` 和 `expectedRevision`。
2. 服务端验证连接身份属于该对局。
3. 服务端验证 `expectedRevision`、当前轮次和目标空位。
4. 五子棋规则模块计算新棋盘、下一手和结果。
5. 服务端在同一事务中追加事件并增加 `revision`。
6. 事务提交成功后才向双方广播权威事件。
7. 数据库写入失败时不广播、不增加版本。

### 5.6 重连

- 每次成功连接先返回完整权威快照和当前 `revision`，随后传递增量事件。
- Godot 忽略已经应用的事件。
- revision 不连续时停止应用增量并请求完整快照。
- 本地未确认动作不能在重连后盲目重放；客户端根据服务端返回的 `actionId` 去重结果决定是否重新提交。

## 6. 对局状态模型

```text
idle
  └─ 原子创建并占用双方槽位 → active
       ├─ 0 步时取消 → cancelled
       ├─ 五连 / 和棋 / 认输 → finished
       └─ 双方连续离线 24 小时 → abandoned
```

`cancelled`、`finished` 和 `abandoned` 都是终态，并在同一事务中释放双方槽位。只有 `finished` 中的获胜或认输结果会计入后续胜负统计；和棋、取消和双方离线作废不计任何一方胜场。

## 7. 持久化模型

首版至少包含以下表：

- `users`：用户 ID、规范化昵称、显示昵称、启用状态和时间戳；
- `invite_codes`：邀请码摘要、创建时间、消费用户和消费时间；
- `refresh_tokens`：令牌摘要、用户、有效期和吊销时间；
- `matches`：游戏、状态、revision、双方离线时间和结果；
- `match_players`：对局、用户、座位和五子棋颜色；
- `match_events`：对局、revision、事件类型、动作 ID、操作者和 JSON payload；
- `active_game_slots`：`gameId + userId` 唯一映射到一个活跃对局。

SQLite 使用 WAL 模式。每一步合法落子都写入 `match_events`，因此即使本期没有记录页面，后续也能从真实事件生成统计和回放。数据库迁移必须由服务端启动流程显式执行并可重复验证。

## 8. 用户流程

### 8.1 首次使用

1. App 启动后发现没有有效 refresh token。
2. 用户输入邀请码和唯一昵称。
3. 注册成功后进入 Flutter 游戏大厅。
4. 后续启动自动刷新登录状态。

### 8.2 空闲用户

1. 五子棋卡片显示“选择对手”。
2. 对手列表显示空闲、离线和游戏中状态。
3. 用户选择空闲对手，服务端立即创建对局并随机分配黑白。
4. Flutter 获取 launch ticket，启动 GodotActivity。

### 8.3 活跃用户

1. 首页五子棋卡片显示对手和“继续对局”。
2. 点击后获取新的 launch ticket 并恢复同一局。
3. Godot 显示当前权威棋盘和轮次。
4. 退出 Godot 后 Flutter 刷新当前状态。

## 9. 错误处理

- 无效或已使用的邀请码：不创建用户，显示可操作错误。
- 昵称冲突：保留邀请码未消费状态，要求更换昵称。
- refresh token 失效：返回注册/登录入口，不降级为游客。
- 对手在创建瞬间变忙：整个事务回滚，刷新列表并提示对方已进入其他对局。
- 非法落子：棋盘保持不变并显示服务端错误。
- 旧 revision：服务端返回最新快照，客户端不自动重放旧动作。
- WebSocket 中断：Godot 显示重连状态并进行有上限的退避重试。
- resume token 过期：返回 Flutter，由 Flutter 获取新票据重新进入。
- Godot 启动失败或闪退：Flutter 提供重试；未落子的对局仍可取消。
- 服务端或 SQLite 写入失败：未提交的动作不广播，客户端保持权威旧状态。
- 日志使用请求、连接和对局关联 ID，不记录邀请码、access token、refresh token、launch ticket 或 resume token 明文。

### 10.2 双模拟器 E2E

仓库脚本必须可以重复执行以下流程：

1. 启动隔离的 Go 测试服务并生成两个邀请码。
2. 构建、安装并清理两个模拟器上的测试 App。
3. 两台模拟器分别注册唯一用户。
4. 用户 A 选择用户 B，服务端随机分配黑白。
5. 测试根据实际颜色轮流落子，并验证两端棋盘一致。
6. 强制停止其中一个 App，再启动并恢复同一棋局。
7. 完成五连并验证双方显示相同结果。
8. 返回 Flutter，验证双方槽位已释放，可以创建新局。

## 11. 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| Flutter 与 Godot 生命周期或打包不稳定 | 实施计划的第一个里程碑先做 Flutter 启动/退出 GodotActivity 的垂直技术样板 |
| 混合渲染和输入问题 | 不使用 PlatformView；Godot 使用独立全屏 Activity |
| 第二个游戏导致五子棋规则渗入平台层 | Flutter、Godot 和 Go 都通过 `gameId` 和注册表隔离游戏模块 |
| 并发创建导致用户参加两局 | `active_game_slots` 唯一约束与单事务占用双方槽位 |
| 客户端作弊或状态漂移 | 服务端权威规则、revision、动作去重和快照恢复 |
| 服务重启丢局 | 每个合法动作先持久化，重启时从 SQLite 恢复 |
| 为未来扩展过度设计 | 首版只实现 Gomoku 模块，不实现通用 DSL、动态下载或多进程集群 |
